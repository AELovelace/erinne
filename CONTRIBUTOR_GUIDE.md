# Contributing to the built-in games

The current repository is Mnemerynne/Erynne. Built-in games open from Media → Games and the set-top-box Media page.

- Register games in `mnemerynne/games.py`. The `multiplayer` flag selects the common casino template and assets; Prism Drop retains its own files. Set `mouse_keyboard=True` on a game a remote or touch screen can't play: it moves to the **Mouse & keyboard** shelf, which only shows where there's a mouse.
- Who is still at a table lives in `mnemerynne/lobby.py` (`PRESENCE`), in memory. Polls and streams report presence there, never to the database. Seats leave through one function per table type (`casino._remove_seat`, `showdown._remove`), so refunds and a stuck blackjack round are handled the same way whether someone left, was removed or went away. A poll that changes nothing must not take the write lock.
- **Lumi in the arcade (2026-11-11).** `static/games/arcade/lumi-sprite.js` (`window.LumiSprite`) draws each player's own Lumi on a canvas.
  - **How it works:** it builds her SVG from Lumi Pet's shapes, her glow palette and `closet.js` (the page loads `lumi-pet/closet.js` first, through `extras`), and caches it as an image per look.
  - **`tidy()`:** keeps only the first of any repeated attribute in the outfit art. A page forgives repeated attributes; a standalone SVG image doesn't.
  - **`draw()`** puts her on the canvas by her paws; **`ball()`** draws her curled up for Yarn Pop.
  - **Whose Lumi:** the shell passes each game's `drawArena`, `drawBoard` and `drawIdle` a `look`, either this player's (`LumiSprite.own`) or each racer's from their showdown seat.
  - **Solo size:** the shell draws a solo game scaled up (`SOLO`), so `arenaPoint()` turns pointer positions back into the game's own 640 × 480 units.
- **Yarn Pop (Breakout) and Lumi Conga (Snake)** share the arcade shell `static/games/arcade/arcade.js`, loaded through the `extras` field in `games.py`. Their slugs, rules and server checks are still Breakout's and Snake's; Snake's `rules.js` also keeps `kinds` (each dancer's colour), which is only drawn. Each game's `game.js` passes it a module: `create`, `step`, `claim`, `board`, `drawArena`, `drawBoard` and the rest. Their `rules.js` and `mnemerynne/arcade.py` must build identical levels and food from a seed; `tests/test_arcade.py` checks this through Node. Use only integer arithmetic below 2**53, so JavaScript and Python agree. A new arcade game sends the server something it can replay or bound, never a bare score.
- Keep authoritative rules in `mnemerynne/casino.py`. API requests contain intentions only. `web/games.py` derives each seat from a signed-in account or authenticated paired screen and applies Media's existing access checks.
- `casino_rooms` (migration 0061) persists full private state. Always use the public snapshot builder for responses: never expose the deck, actor identifiers or hidden dealer card. Mutations run under `BEGIN IMMEDIATE`, and client revisions prevent duplicate moves.
- Coins go through `mnemerynne/coins.py` only, inside the caller's transaction. A casino seat with an `account` plays from that purse: `room()` loads the balance into `chips`, the rules run unchanged, and `_pay_purses` writes the difference. Couch tables have no accounts and use table-only credits. Never accept an amount or score from a browser: Prism Drop's rules live in `mnemerynne/prism.py` for this reason, and any new reward must be something the server saw.
- Keep server text in `textContent`, scripts in static files, and controls usable through `MGame.onAction`. Preserve focus during polling, reduced-motion support, responsive layouts and remote state reports.
- Casino table controls are direct: Left/Right picks, Up/Down adjusts the stake by ten, Enter submits, and Play starts for the host. `common.js` maps media keys and P to `play`; `media.js` routes the remote's existing `toggle` command into the game. Lobby arrows and explicit keyboard Tab navigation retain button access. Do not turn table controls back into focus traversal.
- **Lumi's Lounge** is the tables' look. `static/games/casino/lumi-table.js` is its art, as plain SVG strings like Lumi Pet's art files: `lumi(look, {mood})` draws a Lumi in her 320 × 300 box with `lumi-pet/closet.js`'s clothes, `dealer(mood)` is Dealer Lumi (lilac, visor, vest, bow tie), `chips(amount)` a pile per colour, `pony(i)` a race pony, and `say()`/`seatMood()`/`dealerMood()` decide the words and faces from the snapshot alone, so every viewer sees the same thing. Each coin seat carries `look` (`{glow, outfit}`), which `casino._load_purses` fills from `lumipet.look()`. That function only reads: it never catches her up, counts a visit or makes a pet. Credit seats have no `look` and get a plain Lumi by seat number. Nothing a person typed goes into that markup: glows are looked up, unknown outfit ids draw nothing, and names and speech are set as text. Seat Lumis have no words inside (the browser test compares two players' seat text). On a shared TV each Lumi sits small in her card's corner, and in slots Dealer Lumi perches on the table's edge, because eight cards must still fit without scrolling. `game.html` loads `closet.js` and `lumi-table.js` for every multiplayer game. `tests/js/lumi_table.test.mjs` checks the palettes against Lumi Pet's CSS, the moods, the chips, the ponies and the lines.
- `static/games/casino/roulette.js` owns the persistent SVG wheel, its 37-pocket geometry and ball landing. Reuse it across revisions, honor reduced motion, stop its animation when hidden or destroyed, and always derive the landing from the server result.
- Slots store three horizontal rows and their separate returns. `bet` is per line; use the round's `slot_lines` when reserving, replacing, validating or showing a stake and when computing net results. `wager_lines()` treats pre-update rounds without that field as one line until the next reset. Preserve their original charge and settlement.
- Add explanatory comments around rules, lifecycle transitions and identity handling. Put standalone Python utilities in `python/` and PowerShell utilities in `ps/`.

There is no `game_editor_gui.py` in this repository. These games use the existing registry, templates and rule constants; no separate modding GUI is shipped by this change. Update the player/help and tuning/testing guides when those interfaces change.

See [Testing](TESTING_GUIDE.md) and [Tuning](GENERATION_TUNING_GUIDE.md).

## Lumi-Soft

Lumi-Soft is a cardboard target gallery on the Mouse & keyboard shelf, finished from Doll's GameMaker sniper prototype (`GameMakerProjects\Roulette`, room `rmSniperScope`; the GameMaker project stays untouched). The scope's feel is the prototype's: zoom from the stage (2.5 or 3), the dead-zone pan (140 px of a 1366 screen, 0.12 a step) and Shift to steady the sway, except the still zone is centred where the scope opened, not on the screen.

- **One set of rules, twice.** `static/games/lumi-soft/rules.js` runs the whole run step by step (60 a second); `mnemerynne/lumisoft_rules.py` is a line-for-line copy the server replays before paying. They must agree exactly, so the rules use only + − × ÷ and whole-step timings: no `Math.sin`, no random, no clock. Moves are straight lines, triangle waves and pauses. The scope's sway is decoration only (the server checks where each shot landed, not how it was aimed). Change a rule in both files, then run `node tests/js/lumi_soft_bot.mjs` to re-record `tests/fixtures/lumi_soft_runs.json`; both test suites replay it.
- **The log** is all the page sends: each shot `[step, x, y]` (x and y rounded to a tenth, as both sides read them), each reload's step, how many continues, and the last step. `lumisoft.finish` allows no more continues than `carry_on` was paid for, and no more steps than the wall clock allows (plus 10 s).
- **Stages** are data, `mnemerynne/lumisoft_data/stages.json`, made by `python/make_lumisoft_stages.py` (fixed seeds, so re-running without changes changes nothing). A scene has cover `props` and `waves` of targets; a wave waits for its creatures (not its friends or pickups). Targets stand on their `y` (bottom edge); a pop-up rises from behind the prop on its line. Each stage ends with a `boss` whose `spots` open and close on a cycle.
- **Art** is `art.js` (canvas paths in scene units, so it stays sharp in the scope); every look, prop and boss the stages use must have a drawing (`tests/js/lumi_soft.test.mjs` checks). Your own Lumi comes from `arcade/lumi-sprite.js` (`LumiSprite.draw`). Keep it toys: no real-gun shapes.
- **Prizes** are Lumi Pet catalog entries with `"prize": "lumi-soft"` and a `how` text (house.json, closet.json, art in house.js/closet.js). `lumisoft.PRIZES` maps each to what wins it; `_give` puts it in `pet["decor"]` or `pet["closet"]`. A new prize needs both.
- `window.LumiSoftGame` is a read-only peek (the run, the mode, scene-to-screen) for `tests/lumi-soft-browser.mjs`.

## Lumi Pet

**One pet, three apps (2026-11-10).** Lumi is three entries in `mnemerynne/games.py` on the shelf "Lumi": `lumi-pet` (her room), `lumi-dungeons` (dungeon, battle, skills) and `lumi-garden` (the Stardust Garden). They are not three code bases. All three have `kit="lumi-pet"`, so `templates/game.html` builds each page from the same partial (`templates/games/lumi-pet.html`), the same scripts and the same stylesheet in `static/games/lumi-pet/`; `Game.tabs` says which tabs that app shows, and the partial renders only those buttons. `game.js` reads its tabs from the page (`TABS`), so the rule for new code is: ask `has("dungeon")` (or whichever tab) before offering or drawing something, and never assume a tab exists (`TABS.indexOf` is -1 in the other two apps). `trip()` is the dungeon trip as this page shows it (only Lumi Dungeons draws one); `exploring()` is the plain fact that she is out, which the other two apps turn into `awayRows()`, an empty room (`data-away` on `#lp-room`) and a row that opens Lumi Dungeons. `goHome()` is where a full-room view's "Back" row leads (the app's first tab, or Settings when that view is the first tab), and `LEAVE` renames that row per app. `openApp(slug)` moves between apps: on its own page it navigates, and inside Media's game layer it posts `mnemerynne-game-open`, which `media.js` answers by opening that game properly, so the bar's name and the remote's keys follow. CSS that belongs to the shared page is written against `.gm[data-kit="lumi-pet"]`; `data-game` is the app itself, for the rare rule only one app wants. The server did not change shape: one pet, one save and one API under `/api/media/games/lumi-pet/` for all three, so a new server feature needs no thought about apps, only a tab to show it in. Each app has its own web manifest (`web/app.py` `lumi_manifest`, `/media/games/<slug>/manifest.webmanifest`) and its own icons: Lumi Pet's are hand-drawn (`static/icons/lumi.svg`, `lumi-*.png`), and `python/make_lumi_icons.py` draws the other two from the same face with a badge (it photographs an SVG with headless Chrome, so it needs Chrome but no Python packages). To add a fourth app: a `Game` with `kit="lumi-pet"` and its `tabs`, its words in the partial's `words` table, an entry in `APPS` in `game.js`, and its icons in `make_lumi_icons.py`. The garden reminder opens `/media/games/lumi-garden` (`static/sw.js`); the old address `/media/games/lumi-pet#garden` still works because Lumi Pet's page forwards it.

**The door between Lumi Pet and Lumi Dungeons (2026-11-11).** `house.js` `render()` gives the door spot `data-click="door"` plus an invisible press box (`DOOR_HIT`). An empty door spot draws `door-bare` (`BARE`), so a just-moved-in room still has a door. `game.js` `doorPress` (Lumi Pet only, not while previewing) and the Care row `adventure` call `adventure()`, which sets `#lp-room[data-leaving]` for the trot and then `openApp("lumi-dungeons")`. In Lumi Dungeons, `dungeon-ui.js` `homeRow` is the first row of the places list (game.js `rows()`) and, through `ctx.home`, of a trip's ending. Its `local` reads the ending (`dismiss`) and then opens Lumi Pet. `home` is null in a party. The welcome home is `dungeon-ui.js welcome(run, now)`, called by game.js `welcomeHome` on load and on every refresh. It only counts an ending dated by the server (`ended.at`, set in `lumidungeon.py` `_bank`, `abandon` and `after_fight(..., now)`) that is under `WELCOME_HOURS` old, once per run id per device (`G.store` key `welcomed-run`). Party trips aren't welcomed.

`mnemerynne/lumipet.py` owns Lumi: one JSON document per account in `lumi_pets` (migration 0064), caught up from its last save on every read, with every action validated and saved in one transaction. It was ported from MommyBot's Littlepottchi (`src/dressup/store.js` and `care.js` at `e3a0eda~1`); none of that game's adult mechanics or art come across, and they must never be added to Lumi. The page (`static/games/lumi-pet/game.js`) sends only choices (which snack, which toy) to `/api/media/games/lumi-pet/act`; the server decides every result, and purchases go through `coins.spend`. `rules.js` keeps what only the device knows: local night and day, moods and labels. Items live in `mnemerynne/lumipet_data/items.json`, validated at import, so a bad edit stops the server at start. Needs decay on purpose (Doll's decision, replacing the old no-neglect rule): hunger, energy and joy fall along a logarithmic curve whose last quarter takes one day. At zero Lumi is sad and sleepy, and nothing she owns is ever lost; keep that. Use explanatory inline comments. The full plan (push, house, battles, skill trees) is "Lumi Pet Overhaul Plan (2026-11-09).md" in Doll's BeepDrive Agents folder. The ASCII neon fireplace is a design-list item only.

`mnemerynne/push.py` is general Web Push (subscriptions, RFC 8291 encryption, VAPID), written on `cryptography` and `httpx` with no new dependency; Lumi Pet is its first user. `lumipet.sweep` runs in the worker loop and decides what to send; it keeps its network calls outside database transactions. `static/sw.js` is served at `/sw.js` by `web/games.py` and must stay push-only: no `fetch` handler, and it shows only its own fixed words for known kinds, never text or links from the message. Subscription addresses are checked against `push.PUSH_HOSTS` when saved and again when used; keep that, since it is what stops the server being pointed at internal addresses.

`mnemerynne/lumibattle.py` is the fighting: ported from MommyBot's Touhou Trader (`src/touhou/battleRules.js`, `battles.js`) for the formula, turn order, Defend/Potion/Run, EXP curve, one fight at a time and the turn number that refuses stale buttons. None of Touhou Trader's characters, spell names, art or seed files are used, and none may be added: every enemy and move is original. It never loads or saves a pet; `lumipet.fight_start` and `fight_act` do, in one transaction with the turn. The page's parts are small files under `static/games/lumi-pet/`: `rules.js` (device clock, moods), `house.js` (room art), `closet.js` (accessory art), `enemies.js` (fifteen bodies for twenty enemies), `battle-ui.js` (the Battle tab's lists, pure) and `game.js` (drawing and requests). The art files build SVG markup from strings written in the file, never from anything typed by a person; keep that true. Adding an object, accessory or enemy means a catalog entry in `lumipet_data/` and a drawing in the matching art file; `tests/js/` fails if either is missing. `python/lumi_pet_editor.py` edits the catalogs with the server's own checks. The room is drawn 1000 × 500 and fills its box (the whole screen above 1000px wide, a card on a phone), cropping its sides; furniture is drawn in a 400-wide block in the middle, and Lumi and the fight are placed in the drawing's own units (`--u`, from container query units) so they stay on the rug at any size. The three windows are real holes: `house.js` masks them out of the wallpaper, and when `.parallax` (the neon theme's backdrop, `parallax.js`) is showing, the free view draws nothing so that backdrop shows through. Keep the room's own background transparent, or the holes show nothing. Still to do from the plan: Lumi's minigames (a stretch goal).

`mnemerynne/lumidungeon.py` is the dungeon: it generates a floor (rooms grown from the entrance on a 5×4 grid, the vault always a dead end so its lock never blocks the key, the stairs or the way home), moves Lumi one room at a time, and keeps her satchel until she walks out. Like `lumibattle` it never loads or saves a pet; `lumipet.dungeon_start` / `dungeon_act` do, and `lumipet.fight_act` calls `lumidungeon.after_fight` when a dungeon fight ends. Two rules to keep: `view()` sends the page only rooms she has entered (enemies, loot, the rune code, the winning cup and the card deck stay on the server), and a puzzle is opened by replaying the page's moves on the server (`sokoban_solved`, `lights_solved`), never by the page saying it is solved. `mnemerynne/lumitales.py` is the dungeon's dialogue: a library of lines, a generator (`mnemerynne lumi-tales`, the official `anthropic` SDK with structured output) and live mode. Every line from any source passes `clean()` and is shown as text; keep it that way, since live lines come from a model. TrapQuest was Doll's reference for moving room by room only; none of its content or themes belong here. The page parts are `dungeon-ui.js` (lists and the puzzles as played, pure) and `dungeon-art.js` (a motif per environment, doors, boards, the map). Differences from the plan as built: the way home is the room she came in by rather than a separate exit; rooms are chosen from the list (Go north…) like everything else, since the arrows already move through lists; and the generator makes one request per environment.

**Lumi Pet's controls.** `games/common.js` gives every game eight actions: left, right, up, down, enter, play, and (new) prev and next, which are a remote's track buttons or Page Up/Page Down/[ ] on a keyboard. A remote's Previous and Next only reach a game whose `Game.track_keys` is true (`games.py`; `media.js` checks it), so other games leave them to the music. In `lumi-pet/game.js` `G.onAction` is the whole scheme: prev/next change tab; up/down move through the list; left/right flip the selected row's `options` (or call its `turn`), which is how `picker-ui.js` rows try an accessory on before buying, and swap between house objects she already owns (Home rows list only hers since 2026-11-11; new house things are tried and bought in a spot's whole list); enter chooses. While `walking()` (Dungeon tab open, a trip under way, no fight) the arrows walk or work the puzzle board, prev/next move through the list, and play drinks a potion. For the whole of a trip the tabs are folded away and `render` keeps the page on the Dungeon tab; the list's "Look after Lumi" row opens `dungeon-ui.js` `careRows` (her snacks and a potion, nothing else) instead of another tab. `focus` says whether Enter belongs to the board or the list: the last arrow gives it to the board, the last prev/next to the list. Rows stay plain data built by pure files (`picker-ui.js`, `battle-ui.js`, `dungeon-ui.js`), each tested in `tests/js/`.

**Lumi's health between trips.** The pet holds `wound`, the share of her health that is missing (0 to 1), so it means the same thing after a level-up. `lumibattle.py` owns it: `health`, `hurt`, `mend`, `mends_in`. A trip starts with `health(pet)` and keeps its own `run["hp"]`; going home, giving up or being beaten calls `hurt`. `lumipet.advance` mends it as time passes (`MEND_MS` for a whole bar, `NAP_MEND` times faster during a nap), so it is right however long the person was away. Bought food (`lumipet._eat`) and the `drink` action mend it at home; on a trip food raises the run's count instead. Battle-tab fights never read or change it. The page is told `health: {hp, max, mends_in, out}` and only counts `mends_in` down.

**The dungeon's story panel and mouse.** `lumipet._narrate` gives each moment its line, appends it to the run's `log` (the last `lumidungeon.LOG` lines, sent as `story`) and sets `scene`, the room's own detail from the `look` lines (`lumitales.scene`: chosen by a hash of run, floor and room, so a room is always the same place). The `look` action tells the next detail along. On the page `#lp-story` shows `scene` and the older lines as text, and `#lp-message` the newest; on a trip `.lp-controls` is a flex column so the list and legend sit at the bottom. For the mouse, `dungeon-art.js` `presses` lays see-through shapes over doors, chest, cups, cards, lamps and crate squares, each with `data-click`; one listener in `game.js` turns a press into the same `walk`, `submit` or `boardKey` call the keys make, so there is one path for all three ways of playing.

**The garden's flowers and decorations** are written by `python/make_lumi_garden.py` from short tables (42 flowers, 15 slots of 15 decorations), not typed by hand: change a table and rerun it. A flower's `shape` names a drawing in `garden-art.js` `BLOOMS`, and a decoration slot one in `DECOR`; the catalog refuses a shape the server doesn't list, and the node tests check the page draws every shape and slot and that no two flowers or decorations look alike. Decorations are owned as counts in `state["decor"]` and placed per garden in `garden["decor"]` (`spare` is the difference), so several gardens can each be dressed; the fixed catalog travels once as `garden_decor`, beside the view. In the garden Lumi is moved by two CSS variables on the room (`--gx`, `--gy`, set by `lumiTo`), and each flower's timer is a text node updated in place (`Ga.timers`), so nothing is redrawn to tick.

**Skill trees and the Skills tab.** Each skill in `lumipet_data/battle.json` has `needs` (the skills that lead to it) and `at` ([column 0-2, row 0-5]). The catalog refuses a skill that needs one listed after it, shares a place, or doesn't sit on a lower row than what it needs, so a tree can't loop and always reads downwards; a skill's cost is still `NODE_COSTS` by its position in the list, so a whole tree is 22 points. Because a skill may only need earlier ones, every build learned under the old top-to-bottom rule is still valid. `lumibattle.progress` checks `needs` on `learn`. `skills-ui.js` is the pure part (where each skill is drawn, its state, how the arrows move between skills, the list and words) and `skills-art.js` draws it into the same SVG the dungeon and garden use; `game.js` treats the tab as a mode like the garden (`treeing()`, `skillsKey`, `drawSkills`). **The Collection tab** only reads catalogs the snapshot already carries and what the pet owns (see the next paragraph for how it is drawn). Add a new kind of collectable by adding a shelf in `collection-ui.js` and, if it has a drawing, a `kind` in `collection-art.js` `drawing`.

**Lumi Pet on a phone, and as an app.** The phone layout is one block at the end of `lumi-pet/game.css`, under `@media (max-width: 700px)`: the game becomes a column exactly one screen tall (`100dvh`, nothing scrolls but the list), the left panel shrinks to a strip of meters and coins, the room takes a share of the height that depends on what is in it (more for the garden, trees and collection, where fingers go), and the tabs become a bar that scrolls sideways; `:has()` hides the bar only on a dungeon trip. It is the same page and the same code, not a second version. The touch controls are two elements in the room (`#lp-pad`, `#lp-squeeze`); `drawPad` shows them where `(pointer: coarse), (max-width: 700px)` matches, and their buttons call `onKey`, the same function the keyboard and remote reach, so there is still one path. `choose()` lets a row with only a `local` action through while a request is in flight, so a tap is never dropped. Lumi Pet is an app of her own through `web/app.py` `lumi_manifest` (its own id and a scope of just her page) and the `app_links` block in `templates/game.html`; her icons are `static/icons/lumi.svg` rendered to PNG. The Settings row **Install Lumi Pet** uses the browser's `beforeinstallprompt` offer when there is one. **The Collection** is a mode like the trees: `collection-ui.js` (shelves, paging, cursor, words) and `collection-art.js`, which borrows each thing's drawing from the file that already draws it (`house.js` `ART`, `closet.js` `ART`, `garden-art.js` `bloom` and `piece`) and marks each frame `data-thumb`; `fitThumbs` in `game.js` then sets every frame's viewBox to its drawing's own bounding box, so no per-thing coordinates are kept anywhere.

**The Stardust Garden.** `mnemerynne/lumigarden.py` holds every rule; one JSON document per person in `lumi_gardens` (migration 0069); the catalog is `lumipet_data/garden.json`. Growing is only timestamps: a plot stores `ready_at` and `grow`, and watering, fertilizer and the Mage's ability move `ready_at` earlier, so nothing ticks and nothing is replayed. `rates()` is the one place every number comes from (helper levels, the skills learned in each tree, `lumibattle.bonuses`, her level, permanent upgrades, running effects). `advance()` pays the Monk's squeezing since the last look: full rate while the page is open, the kept share for up to the away limit after a gap; only `lumipet._garden` calls it (from `snapshot` and `garden_act`), never the reminders sweep. Coins leave only through `_squeeze`, as whole coins paid by a running count (`coins.prize` with a ref), priced by `price()` from how many were made today. Flower kinds are unlocked per garden on a tree (garden.json `branch` and `after`, written by `python/make_lumi_garden.py`): `lumigarden.opens()` allows a flower once any one of its `after` flowers is unlocked, and `load_catalog` refuses an `after` that isn't listed earlier, so the tree can't loop; each flower is still gated by that garden's `given`, her level and its price; Moonrise replaces the garden with `_starter()`. Presses are the one thing the page counts: the server accepts about twelve a second and decides what they made. The watering sequence stays on the server and the page is sent only this round's part. On the page, `garden-ui.js` (rows, words, number format), `garden-art.js` (drawing, `data-click` shapes), and `garden-tree.js` / `garden-tree-art.js` (the Flower tree, Helpers and Moonrise pages: the `seeds`, `helpers` and `moon` drawers, drawn over the garden like the Skills tab, with `tree:<id>` clicks) are pure and tested in node; `game.js` treats the Garden tab like a trip (`gardening()`, `gardenKey`, `gardenSend`, `drawGarden`; `paging()`, `pageEnter` and `drawPage` for the three pages, each with its own cursor in `pageCursor`), batches presses once a second, and listens for `pointerdown` so a press is never lost to a redraw. `drawList` now changes a list's words in place when its rows are the same, for the same reason. The reminder is the `garden` kind in `lumipet.sweep`, from `lumigarden.ready_since`.

**Lumi Dungeons with friends (2026-11-10).** `mnemerynne/lumiparty.py` is a party of up to three on one shared floor.

- **Storage.** One JSON document per party in `lumi_parties`, and `lumi_party_members` keeps each account to one party (migration 0073).
- **Shape.** It follows `showdown.py`. `act()` reads the party, catches up its clocks (`_advance`: a vote's 20 seconds, a puzzle turn's time, a holder or fighter gone quiet), does one thing, and writes and wakes `HUB` only if the document changed. `look()` takes the write lock only when `_due()` says a clock has run out. Presence is `lobby.PRESENCE` under `("lumi-party", code)`, keyed `user:<id>` online and by the TV's actor for couch members.
- **Floor and loot.** The floor is `lumidungeon.generate` with an empty pet, because loot is rolled per member when it is taken (`_take`). A chest gives everyone standing the same coins and potion; the vault runs `_vault_loot` and `_set_piece` for each member.
- **Votes.** Each member has a `vote`, settled by `_tally`. A majority settles it at once, and so does everyone having voted. Otherwise the most votes win after `VOTE_SECONDS`. Ties go to the dice, except a tie between members, which goes to whoever has the fewest `puzzles`.
- **Puzzles.** A puzzle is `run["puzzle"]`. It starts in `pick` (voting who goes first), then moves to `attempt`. `_pick` fixes the `order`: the chosen member, then the fewest tried (by seat), then the last. `turn` moves round that order in `_fail`. Only `holder()` may move it. Crates and lamps are sent as the moves so far (`_sokoban_progress` checks every step is legal), so the others can replay them.
- **Fights.** Each standing member gets one `lumibattle.start(..., party=code)`. `lumipet.fight_act` sees `fight["party"]` and hands the end to `lumiparty.after_fight`, which settles the room once nobody is still fighting (`_settle_fights`).
- **What the page sees.** `view()` gives the page a run shaped exactly like `lumidungeon.view`, plus `run.party` (options, votes, puzzle, deadlines). So `dungeon-ui.js` and `dungeon-art.js` draw a party trip unchanged, and `lumipet.snapshot` puts it in `dungeon.run`.
- **The page (`game.js`).** The solo page's own buttons mean the same at a party (`move` votes a way, `leave` votes home). So `game.js` only:
  - redirects `dungeon/act` rows to the party (`submit`);
  - adds the rows in `party-ui.js` (`startRows`, `lobbyRows`, `tripRows`);
  - sends the holder's crates and lamps move by move (`partyProgress`);
  - rebuilds a watched board from the server (`partyBoard`).
- **The couch (`couching()`).** The TV owns the party (`display`).
  - Every remote press arrives with its signed `controller` and its plain remote id; `media.js` now forwards both.
  - The TV keeps one cursor per member (`couchCursor`, reset when their menu changes) over `Pu.couchMenu`.
  - OK is sent as `POST …/parties/<code>/tv/input` with the press's proof. `web/games.py` checks it with `_live_remote`, then `lumiparty.couch` acts as that remote's own account.
- **Out on a trip.** A party member can't start a solo trip, an arena fight or a garden action (`lumipet` checks `lumiparty.on_trip`).

**TV guests and Who's playing? (2026-11-10).**

- **Guests.** `media/screens.py` has `guests`, `add_guest`, `remove_guest` and `drivable` (migration 0072, `media_screen_guests`). An owner makes another account a guest on all of their TVs.
- **Guest commands.** `remote_command` uses `drivable` and builds a guest's command as the TV's **owner** (`_command(conn, owner, …)`), so what plays comes from the owner's library. `sender` is the guest.
- **One check for presses.** `web/games.py` `_live_remote` checks that a signed press may still drive a TV: the proof is for this screen and pairing, the remote's owner is the TV's owner or a guest, and they are still in the screens group. Casino `tv_input`, the party's couch input and Who's playing? all use it.
- **Play pass.** `mnemerynne/lumi_tv.py` issues a play pass for a remote's OK on a TV (`POST /api/media/games/lumi-pet/tv/player`). The Lumi page sends it as `X-Lumi-Player` through `MGame.setHeader`.
- **`pet_user`.** This dependency is on every Lumi route except push. It loads the pass holder instead of the TV owner, and refuses with 403 (never falling back) once the pass stops holding.
- **Page flags.** `game.html` sets `data-who` when the TV's owner has guests (this shows the picker) and `data-tv` on a TV as its owner (this offers Party on this TV).

**Co-op fights, stat points, fight items, naming and moving in (2026-11-11).** A party's fight is no longer one `lumi_battles` row each: it is `run["fight"]` inside the party document, played by `lumibattle.team_start` / `team_act` / `team_skip` / `team_drop` (pure functions on that dict: Lumis in seat order, then the creatures, in rounds; `turn` counts every action, so a stale press is refused) and settled by `lumiparty._team_end` (each pet's EXP via `team_finish`, ghosts, the room). Because it lives in the party, the party's stream carries every turn live; the page reads `party.run.party.fight` (`_public_fight`: bars, stages, `pocket`, whose turn and until when). Old one-each fights still finish through `after_fight`, so a fight in progress at a deploy isn't stranded. Each fighter's `pocket` (potions, kit) rides on the fight so every page (and the couch) can show what that player can give; the giver's own pet pays (`take_item`). Fighter names come from `_fighter_name` ("jane's Lumi" when two share a name). Party members also carry `pet`, `colour` and `outfit` so pages can draw each friend's Lumi (`game.js drawCrew`, `lumiMarkup`: the template's own Lumi shapes, copied once, in their colours via CSS variables).

Stat points: `lumibattle.lumi_base` (half fixed growth plus points), `place_auto`, `level_up` (the one place EXP turns into levels, so Auto on level-up always applies), `settle_points` (an older save's points, placed once by `lumipet.load`). Enemies still use `base_stats`. `stat_of` applies X-item stages; `item_refusal` / `use_item` / `take_item` are the item rules for both kinds of fight.

The pet has `name` and `colour` (`#rrggbb` or None; her element stays `glow`). `lumipet.look()` returns both for other games (casino, arcade). `rules.js` turns a colour into her three CSS colours (`tint`, `looks`) for everywhere she is drawn.

Moving in: worn pieces (`"worn": true, "box": N`, written by `python/make_lumi_worn.py`, art in `house.js`) are free but only owned once unpacked (`lumipet` action `unpack`, one a day by `coins.today`). `placed()` leaves a spot whose first object is worn out of the house (bare); `house.js render(house, backdrop, {boxes})` draws bare plaster and concrete (`wall-bare`, `floor-bare`) and the box stack. `lumipet._move_in` ran once per pet (`moved_in`), refunding by `lumi-move-in:<user>`. The picker's `ask` (and `game.js choose`) is try-before-you-buy: the first press previews, the second buys. The party browser is `party-ui.js browserRows/browserScene`, drawn in the room's always-visible middle strip (x 350–650, like the gallery).

## One TV, multiple casino remotes

The casino lobby on a paired, non-speaker TV offers **One TV, multiple remotes**. It creates a display-only host surface, leaving all eight player slots available. Each paired remote's first Enter joins its own seat; subsequent keys affect only its persisted `controls` draft. The first player is host. Normal account/device tables and guests joining their code retain the original controls.

`casino_remote.py` signs the authenticated panel's exact key for the destination screen and current device pairings. `web/media.py` adds this proof to press/Play commands; `media.js` and `games/common.js` preserve it through the iframe. `web/games.py` verifies signature, 90-second expiry, current pairings, ownership and screen access before `casino.couch()` processes it. Never trust a browser-supplied remote ID or use a remote name as identity. Device fingerprints and input receipts stay out of public snapshots.

`casino.couch()` serializes each key, draft, join and bet in one database transaction. Receipts suppress replay across TV refreshes, duplicate stream listeners and workers. Round/phase checks prevent a delayed betting Enter from becoming Hit. The client queues remote inputs independently of the ordinary button busy flag. Keep the viewer spectator-only, show every player's draft/hand/results, and preserve host transfer after explicit seat removal. There is no new schema migration: display and controller metadata live in the existing room JSON.

## TV game scaling

`web/app.py` gives built-in game iframe requests the TV's text-size context, with zero extra underscan and no kiosk toolbar/listener. Other embedded pages retain their existing behavior. Games reuse `erynne.css`'s root `--ui-scale`, including automatic 1×/1.5×/2× sizing and saved manual sizes. `media.js` sends the current scale on iframe load, window resize and live Text size adjustments; `games/common.js` accepts it only from its same-origin parent on a TV, then asks canvas games to resize. Use rem for layout caps (casino 100rem; Lumi Pet 112.5rem wide, room 47.5rem tall) so controls and artwork grow together. Keep SVG viewBox/canvas world coordinates fixed; redraw canvas pixels from its CSS size and device pixel ratio.
